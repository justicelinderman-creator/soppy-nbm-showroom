A lead form can appear to work while quietly duplicating records or losing requests. Use this checklist to test how a proposed n8n intake workflow handles the unexpected, before connecting real people or sending messages.

BEFORE YOU TURN IT ON.

01 / INPUTS

Define one entry route

Agree whether the workflow receives an n8n form, website webhook or approved application event. Name the mandatory fields and reject malformed payloads before any action is attempted.

Test: valid, missing and invalid fields.

02 / IDENTITY

Decide what "duplicate" means

Email normalization is not the same as a durable exactly-once guarantee. Specify a key, replay window, storage, retention and what happens after a server restart.

Test: repeated submissions, case variations and restart replay.

03 / PERMISSION

Keep customer contact consent separate

An incoming form is not blanket permission to send marketing. Record the customer's allowed contact purpose and use an approval step before any new outbound route is activated.

Test: no consent, withdrawn consent and authorized acknowledgment.

04 / ERROR HANDLING

Make rejection visible

Use explicit branches for missing credentials, invalid payloads, timeouts and API errors. Do not silently mark a partial flow successful.

Test: rejected request, expired token and failed destination.

05 / RETRIES

Retry only with a known contract

Repeated POST requests can create duplicate side effects. Confirm the target service's idempotency and retry semantics. Uncertain network outcomes need reconciliation before reattempting.

Test: temporary 429/503, repeated delivery and ambiguous timeouts.

06 / OUTPUTS

Read back the accepted result

An HTTP success code does not prove a record reached the correct destination. Inspect an approved staging table or verified receipt with the expected record identity and number of items.

Test: complete, missing, duplicate and partially written destination.

07 / PRIVACY

Minimize and protect information

Use synthetic inputs in demonstrations. Keep real API credentials out of Git history and external proposals. Avoid logging customer email, secrets or payloads unnecessarily.

Test: redacted exports, safe error logs and least-privilege access.

08 / HANDOFF

Keep the owner in control

Document setup, required accounts, configuration and rollback steps. The client should know what happens on a failure and how to disable a misbehaving workflow without losing evidence.

Test: staged deployment, rollback and owner review of all outbound changes.
